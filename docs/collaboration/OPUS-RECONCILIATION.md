## Native Mac experiment and verification package

Candidate: native SwiftUI shell plus bundled existing Python runtime, with a
small native bridge for permissions, secret handles, notifications and IPC.
This is an experimental preference, not a framework mandate or a Swift rewrite.
Tauri and Electron remain alternatives until measured on actual macOS.

| Option | Evidence-backed tradeoff | Verification that decides |
| --- | --- | --- |
| SwiftUI / native shell + Python | Direct native integration; retains institutional Python code. Native IPC, packaging and update work remain. No measured memory/velocity advantage claimed. | Signed helper identity, UI closure, launch lifecycle, Python bundle, permissions and update rollback |
| All-native rewrite | One implementation language but porting canonical Python semantics adds large verification cost | No demonstrated residual deficit justifies this rewrite |
| Tauri + Python sidecar | Web UI with window/plugin capability controls; overlapping capabilities combine permissions; custom commands need explicit restriction | Webview/IPC denial tests, native plugin burden, signed sidecar lifecycle, memory measurement |
| Electron + Python sidecar | Mature web tooling; renderer security and dependency update burden; remote content must not gain Node privileges | Context isolation, sandbox, IPC sender validation, permission denial, signed updates, measured footprint |

Sources: [Apple launchd lifecycle](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html),
[Tauri capabilities](https://v2.tauri.app/security/capabilities/),
[Electron security](https://www.electronjs.org/docs/latest/tutorial/security),
[Tauri signing](https://v2.tauri.app/distribute/sign/macos/),
[Electron signing](https://www.electronjs.org/docs/latest/tutorial/code-signing).
The Apple lifecycle source is archived: per-user agents end at logout. It does
not prove current SMAppService behavior. Modern Apple DocC pages were discoverable
but their API bodies were not retrievable here; verify against the target SDK.

Native acceptance procedure (not executed):

1. Record physical device/OS/SDK, exact signed build, Python/package manifests;
   use a test account, no production secrets and explicit machine-owner consent.
2. Inspect SMAppService/login-item registration and approval on that OS. UI quit
   must leave authorized work running; user stop must stop it. Distinguish logout,
   lock, sleep/wake, process crash and reboot. Sleep is not available compute.
3. Authenticate the founder through the separately reviewed enrollment/custody/
   revocation path. Local user/session or workload authentication alone is not
   Alfonso. Bind each command to scope, freshness and idempotent application ID.
4. Restrict IPC peers (XPC/code identity or an equivalently tested mechanism).
   Reject an unapproved client and replayed/altered messages. The UI owns no Gate.
5. Test Keychain handle retrieval and denial in a disposable item namespace;
   generated workers receive no vault. Test revocation, restart and locked-device
   behavior. Never print secrets. Test Accessibility, Apple Events and screen
   capture permission denial/revocation separately; no broad permissions by default.
6. Submit one real bounded mission, close UI, wait for its due trigger, interrupt
   after acceptance, recover under an independent OS supervisor, reconcile once,
   retain an exception, accept an authenticated scoped mission update, and resume.
7. Inspect the morning report against independent observations. Attempt a forged
   success and hostile source instruction; neither may cause a permission or
   outcome change. Record intervention count, latency, full process-tree resource
   use, failures and real outcome. Run pause, safe mode, uninstall and restore.
8. Before distribution, verify Developer ID signing, notarization, update
   signatures and interrupted-update rollback on a real Mac. No signing keys,
   installer execution, service registration or native pass is claimed here.

Phone access later uses a paired authenticated channel to the same host state,
with revocation, command freshness, scope and explicit pause. It is not a second
mission store or a reason to expose an unauthenticated listening service now.
