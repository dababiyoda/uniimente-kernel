## Five review roles

These are five perspectives recorded by the same assistant, not independent
reviewers or manufactured consensus.

- Builder: complete the causal chain using existing APIs and contracts. The
  output must visibly contain citations, assessment disagreement and pending drafts.
- Adversary: popular repositories can change licensing; search snippets can be
  wrong; models can invent citations or instructions. Compare upstream licenses,
  require known source IDs, reject extra authority fields, retain observations
  as unverified and bound input/output. This is attribution, not fact checking.
- Operator: avoid a new scheduler and hosted dependency. Pin consumer revisions,
  search image digest, model-server version and reporting package. Verify ledger
  recovery and drift refusal. A timed-out workspace requires CI evidence, not a
  fabricated local pass. Local services and hardware remain deployment dependencies.
- Beneficiary representative: search queries leave the host through search engines;
  keep private documents in supplied excerpts, and do not treat drafts as reviewed
  public advice. No outreach or publication occurs. Accessibility and utility of
  final media still require a real audience review.
- Constitutional reviewer: use one canonical spine and existing ratification;
  previews are explicitly synthetic; production CLI cannot create its own approval.
  Wire data is not a verified transport identity. No canonical Foundry qualification,
  passport, capability grant, payment or authority plane is invented.

## Pass 1: structural inversion

Advantages can become retained evidence, interoperable wire contracts, reusable
drafts and a reduced API cost floor. They reverse into liabilities if license
drift, bad source quality or maintenance overwhelms saved time. Bind versions,
record source types and carry warnings/gaps.

Disadvantages: uncertain data, unknown hardware and workflow failure. Bound data
sizes, stop at pending review, keep sources and assessments, isolate consumer
configuration, and use canonical checkpoints. Search-engine failures remain
observable. Runtime drift invalidates the configuration hash. This architecture
exists to reduce repeated manual work; the metaphor was not literalized.

## Pass 2: adversarial compounding

Re-attack the strengthened version: a single local server can fail; a high WMI
score can be mistaken for market evidence; a template preview can be mistaken for
AI or customer proof; source code can change after approval; a resumed workflow
can repeat a completed stage. Preserve explicit mode/status fields and unproven
market validation, bind source revisions and adapter files, reject changed source
checkouts, and test persistent restart and withdrawn ratification. Do not add
paid fallback, extra autonomous actors or a second event ledger to hide failures.

Pass-1 downsides remain: model factual quality is not solved by schema validation,
search sources can be wrong, and hardware is unknown. Owner is the existing Kernel
operator (Alfonso or a named delegated maintainer). Kill thresholds below apply.
Underlying advantage is falsified separately: if real reviewed outputs do not save
operator time or support a useful validation decision, working architecture is
insufficient evidence and the line should regress to manual composition.

## Evidence, dissent and operating decision

Required implementation evidence: core boundary tests, persistent interruption/
resume, real WMI/DALEOBANKS computation under mocked local HTTP, and an exported
synthetic preview. Existing canonical schema/authority/sealed checks remain.
Actual Actions results are recorded in the PR, including failures and fixes.
Counterevidence from upstream source review: python-dotenv v1.1.1 does not honor
PYTHON_DOTENV_DISABLED. The initial composition checks passed without an env file,
which did not prove that isolation boundary. Pin v1.2.3, refuse unsupported loaders,
and add a real-child env-file test before accepting the boundary.

Unresolved dissent: neither popularity nor local execution proves factual accuracy,
a buyer, adoption, willingness to pay or business advantage. Browser capture,
PDF/OCR and full audio are still unimplemented adapters. No model downloaded or
Docker/GPU deployment tested in this session. Retain these limits.

Migration: additive modules and runbook; no package-boundary wheel expansion.
Previously merged local-model defaults remain. Existing manual/template paths
and registered consumer APIs remain intact. Reverting the assembly invocation or
additive files rolls it back; ledger evidence and prior branches stay retained.

Kill criteria: any paid/hosted fallback, automatic approval/publication/contact/
payment, fabricated source or buyer demand, changed code/config accepted under an
old pattern, damaged evidence history, or repeat of an unacknowledged consequential
operation. Regress the line if reviewed outputs fail factual/editorial review in
the operator's first real pilot or do not reduce preparation time relative to the
manual baseline. Name and measure that baseline on the actual target machine.

Decision: experiment. Merge tested composition as an available capability; do not
equate installed code or synthetic success with production effects or market proof.
