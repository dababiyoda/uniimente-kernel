## 8. Refutation of the integration-path choice

The strongest counterargument is not "adopt #137"; it is that **the chosen path does not satisfy the directive's own integration instruction under either reading of "GREG".**

§22 opens with "inspect the current canonical GREG path" and §32.6/32.8 say "turn the current GREG into the first integrated version of this loop" and "Connect it to the existing persistent GREG runtime." Two candidates exist for "existing persistent GREG runtime":

- On main, the only persistent standing runtime is `egregore/runtime.py::StandingCognitionRuntime`. PR #160 does not connect to it (verified: no import, no seam, separate trigger discipline). The synthesis concedes this in dissent 1 and makes the seam build item 1, but then classifies A–I as EXISTING and calls the path "extend kernel main through egregore/". By §32.8, what exists is a sibling package that shares a ledger; the directive's integration step is the part that is still MISSING, and the synthesis puts it in the backlog rather than in the status.
- Across the PR graph, the only lineage with a persistent *body* (SIGKILL-tested, supervisor-run, cadence-driven) is #137's `greg/`. The directive says "the current GREG" and "persistent GREG runtime", wording that fits #137's body far better than main's test-driven `tick`. The synthesis rejects #137 on grounds (a) founder Ed25519 envelopes create a second authority plane; (b) kernel-core modifications and dev deps; (c) missing B/D/G/F; (d) private `_eval_view` use; (e) adopting it is the founder's merge decision. Counter to each: (a) is a reason to strip `greg/founder.py`, not to abandon the body; the founder-auth plane is also absent from #160, which carries "declared lineage, not authentication" and thus has the same G6 gap; (b) the torn-tail quarantine and `_eval_view` precheck are exactly the restart-continuity mechanisms the synthesis says it will "port with credit", so the dependency is being re-derived, not avoided; (c) #160 is equally missing a scheduler, Genesis builder, kill test and real sensors, so "missing pieces" cuts both ways; (e) choosing #160 as "the candidate implementation" and asking Alfonso to ratify it is the same class of founder decision as asking him to ratify #137, dressed as the default.

The consequence the synthesis does not state: by building on main and deferring #137 "until the founder rules", the path guarantees that on the day of the ruling there will be **four** goal/mission engines (#160 `egregore/goals.py`, #137 `greg/missions.py`, #109 `egregore/goal_chase.py`, #101 `local_mission.py`) instead of three, each with tests, each preserved by the Final Build Order, and the reconciliation cost it attributes to #137 will have been increased by its own work. The simplest-viable alternative that the directive actually asked for ("minimal architectural changes required to turn the current GREG into the first integrated version") was to add goal persistence, relevance routing and intersection detection *as proposers and records inside `StandingCognitionRuntime.tick`* (which already accepts `context=` and hands proposers the full signal tuple) and to keep #137's body as the host candidate. The synthesis's own reuse table shows every primitive needed for that route already exists; it never explains why a new loop class with its own turn/hydrate/conflict machinery beats adding proposers to the existing tick, which is the question the Anti-waste rule and §31 require it to answer.

Secondary refutations: the "merge baseline" argument (main 626 green vs #137 needing dev deps) is an environment fact, not an architecture fact, and the same `requirements-dev.txt` is needed for the fail-closed `date-time` format check the synthesis itself mandates; and the "staged reversible experiment" claim (rollback by reverting one commit) is weakened by the governance footprint already committed on the branch (intent record, ledger section, ADR, manifest capability, verifier criteria, closure registry), none of which the rollback plan enumerates.
