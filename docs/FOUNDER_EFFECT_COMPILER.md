# Founder Effect Compiler Doctrine

Status: **ACTIVE FOUNDER INTENT**  
Owner: Alfonso Lopez  
Intent record: `docs/intent/INTENT-0030-effect-not-metaphor.md`  
Applies to: UNIIMENTE Kernel, every organ, every Venture Cell, every coding/research agent, every future repository or tool acting on UNIIMENTE work.

## Governing correction

Founder language describes the **desired effect, invariant, or capability** unless Alfonso explicitly says the implementation itself must be literal.

Metaphors such as **egregore, organism, morphogenesis, organ, cell, tissue, immune system, metabolism, healing, regeneration, nervous system, embodiment, omniscience, Jarvis, self-improvement, or immortality are mechanism-discovery prompts and outcome specifications. They are not instructions to imitate biology, mythology, or science fiction in software.**

The standing rule is:

> **Preserve the effect. Do not preserve the metaphor's surface form. Translate the founder's aspiration into a falsifiable target effect, then use the simplest lawful, evidence-backed, resourceful mechanism that can actually produce that effect.**

If a science-fiction formulation is impossible literally, do not silently shrink the destination and do not fabricate capability. Determine the underlying result Alfonso is trying to obtain and search for the strongest mechanically real approximation or realization using currently available technology.

## Why this exists

Prior agents over-literalized founder language and spent material engineering effort building digital analogues of biological morphogenesis, cells, tissues, developmental fields, and organizational morphogenesis as though those surface metaphors were themselves the requirement.

That work is preserved as research, evidence, mechanisms, competitors, and historical lineage. The **literal framing is regressed**.

The founder's intended meaning is functional and resourceful:

- if a capability is missing, acquire, compose, adapt, or build it;
- if a function breaks, restore the function by the best available mechanism;
- if a goal sounds impossible, decompose the desired result until real mechanisms become visible;
- use biological, institutional, technical, or science-fiction analogies as **mechanism mines**, not implementation mandates;
- prefer commodity infrastructure, open-source projects, APIs, plugins, computer use, external tools, and small generated utilities before inventing a new substrate;
- invent only when existing mechanisms cannot satisfy the effect with acceptable reliability, authority, cost, and evidence.

## Mandatory Effect-Compilation Loop

Every materially novel founder request must pass through this interpretation sequence before architecture is chosen:

```text
FOUNDER EXPRESSION
    -> preserve exact source language and lineage
    -> identify intended real-world or digital effect
    -> separate literal requirements from metaphor / aspiration
    -> define observable success and falsification conditions
    -> inventory capabilities already present
    -> search existing commodity/open-source/API/tool mechanisms
    -> extract transferable mechanisms
    -> mutate/recombine mechanisms where useful
    -> identify residual CapabilityDeficit
    -> acquire / compose / adapt / build only what remains missing
    -> sandbox and test
    -> independently verify at the strongest available evidence tier
    -> attach capability under an explicit authority envelope
    -> resume the original goal
    -> measure reality
    -> RETAIN / MODIFY / REGRESS / KILL
```

This is the canonical relationship between founder intent, the Infinite Goal Chase, Mechanism Recombination Foundry reasoning, capability discovery, Capability Genesis, and eventual organ formation.

## Resourcefulness ladder

Before creating new architecture, test these routes in order unless evidence justifies skipping one:

1. **Use an existing UNIIMENTE capability.**
2. **Reconfigure or compose existing capabilities.**
3. **Use mature commodity infrastructure.**
4. **Adopt or adapt an open-source project.**
5. **Use a supported API, plugin, connector, model, or service.**
6. **Use computer control to operate an authorized external tool or development environment.**
7. **Generate a small bounded utility or adapter.**
8. **Commission a coding agent or temporary specialist team to build a missing capability.**
9. **Use OMNIMORPH when organization design is actually the bottleneck.**
10. **Invent a new architecture only when the preceding routes cannot satisfy the target effect.**
11. **Escalate to Alfonso, wait, or abstain when the missing requirement cannot be achieved within current law, safety, authority, budget, evidence, or technology.**

The list is a decision prior, not a rigid algorithm. The cheapest decisive mechanism may appear later in the list. Agents must explain why a more complex route is warranted.

## Canonical meaning of morphogenesis

For UNIIMENTE, **morphogenesis is functional capability formation in response to a verified discrepancy or CapabilityDeficit.**

It means the institution can change its functional form so that it can continue pursuing an authorized goal.

Examples of valid morphogenetic outcomes include:

- discovering and attaching an existing tool;
- adapting an open-source project;
- composing several capabilities into a new workflow;
- writing a narrow missing utility;
- commissioning a coding agent to build a tool against a frozen contract;
- creating a temporary agent team when parallel specialization is advantageous;
- forming a persistent organ after repeated evidence shows the function should become durable;
- restoring a lost function with a materially different implementation;
- deciding that restoration of the original is cheaper and safer than novelty.

Morphogenesis **does not require** simulated cells, tissues, local developmental rules, decentralized topologies, emergent spatial patterning, or dynamically generated organizations. Those remain optional research mechanisms and must beat simpler baselines for the problem at hand.

## Effect examples

### "Heal yourself"

Compile to: detect functional degradation -> localize the lost capability -> find/acquire/build repair -> verify restoration -> reconcile interrupted work -> resume.  
Do not require a digital wound-healing simulation.

### "Grow a new organ"

Compile to: a recurring capability deficit has become important enough to justify a bounded reusable subsystem with explicit contracts, authority, state, tests, lifecycle, and shutdown.  
The subsystem may be ordinary software if ordinary software solves the function.

### "Give UNIIMENTE an immune system"

Compile to mechanisms such as identity, anomaly detection, least privilege, quarantine, revocation, sandboxing, incident memory, rollback, and recovery.  
Do not simulate leukocytes unless a biological mechanism itself is experimentally useful.

### "Make UNIIMENTE immortal"

Compile to continuity of founder intent and institutional capability across component failure: replaceable models, reproducible infrastructure, durable state, provenance, backups, succession, recovery, migration, vendor independence, and shutdown-safe restoration.  
Do not claim literal immortality.

### "Become omniscient about my businesses"

Compile to minimizing decision-relevant unknowns through authorized data access, sensing, retrieval, memory, contradiction tracking, freshness, and uncertainty reporting.  
Do not claim omniscience.

### "Watch over / protect me in the physical world"

Compile to the lawful protective effects actually sought: founder-consented location/context when authorized, public situational-awareness data, hazards, weather, traffic, emergency information, relevant public camera context where lawfully accessible, anomaly detection, early warning, and concise escalation.  
Do not fabricate ubiquitous physical surveillance, bypass access controls, perform unauthorized face recognition, or claim continuous tracking that the available mechanisms cannot prove.

## Capability Genesis contract

A capability created or acquired through this doctrine must record, at minimum:

- CapabilityDeficit and founder-intent lineage;
- target effect and acceptance tests;
- source mechanism / repository / service provenance;
- license and dependency constraints when applicable;
- builder identity and build environment;
- data and network permissions;
- cost and resource ceiling;
- authority envelope and consequence class;
- sandbox/test evidence;
- independent verification evidence or explicit absence thereof;
- known failures and unsupported cases;
- attach/detach/rollback procedure;
- lifecycle state and owner;
- review and kill conditions.

**Building software does not authorize installation. Installation does not authorize activation. Activation does not grant consequence authority. A new capability never inherits the authority of the process that requested or built it.**

## Anti-literalization gate

Before implementing a founder metaphor or science-fiction statement, an agent must answer:

1. What observable effect is actually desired?
2. Which parts of the founder's wording are literal requirements, and which are analogy or aspiration?
3. What is the simplest conventional mechanism that could produce the effect?
4. What existing open-source, API, plugin, service, computer-use, or repository mechanisms can be reused?
5. Which mechanisms from the metaphor are causally valuable after branding and surface form are discarded?
6. What remains genuinely missing?
7. Why does the proposed implementation beat the simplest viable alternative?
8. How will the claimed effect be falsified or externally verified?

If these questions are not answered, implementation is premature.

## Prohibited interpretation failures

Agents must not:

- treat metaphorical language as a requirement to reproduce the source domain's surface form;
- build a new framework merely because the founder used a biological or science-fiction term;
- silently weaken the founder's destination because literal realization is currently impossible;
- claim an impossible capability was achieved because an internal simulation resembles it;
- confuse mechanism research with operational capability;
- equate an agent hierarchy with intelligence or morphogenesis;
- equate organizational complexity with capability growth;
- force blockchain, zero trust, biology, swarms, or any favored technology into a solution when it is not causally required;
- build when an existing tool or project can satisfy the target effect more cheaply and reliably;
- let generated code or newly acquired tools self-authorize, self-promote, or inherit privileges.

## Evidence rule

A successful translation is proven by the **underlying effect**, not by resemblance to the metaphor.

Examples:

- an "immune system" succeeds when attacks or failures are detected, contained, recovered from, and learned from;
- "regeneration" succeeds when lost function returns under preserved authority and obligations;
- an "organ" succeeds when a bounded specialist capability repeatedly produces verified value;
- "Jarvis" progresses when Alfonso can actually delegate goals, receive useful escalations, and get verified outcomes with declining intervention.

Surface similarity is irrelevant unless Alfonso explicitly makes it part of the requirement.
