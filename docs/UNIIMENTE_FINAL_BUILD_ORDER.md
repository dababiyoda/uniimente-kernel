# UNIIMENTE FINAL BUILD ORDER

## CRITICAL ARCHITECTURAL OVERRIDE

**Preserve Everything. Connect Everything. Convert Every Useful Component into an
Institutional Capability.**

This order supersedes any instruction elsewhere that tells you to delete
implementations, erase duplicated code, discard branches, remove legacy modules, or
collapse the repositories by destroying previous work.

Do not delete valuable code, tests, documents, branches, proof records, schemas,
experiments, failed approaches, or historical implementations.

Do not destroy institutional memory to create architectural neatness.

The objective is not to make the repositories smaller. The objective is to make every
useful component: discoverable; understandable; interoperable; governable; testable;
attachable; detachable; replaceable; recoverable; and reusable by the complete
UNIIMENTE organism.

Preserve the entire evolutionary record. Connect what is disconnected. Control what
overlaps. Activate only what is authorized.

## 2. Absolute Preservation Rule

Do not destructively delete anything unless it is: malware; exposed secret material;
legally prohibited content; corrupted generated debris with no evidentiary value; or
an exact byte-for-byte duplicate whose original remains cryptographically preserved.
Even then, document the action.

For ordinary superseded implementations: preserve the source; preserve the tests;
preserve the reason it existed; preserve its known advantages; preserve its failures;
preserve the commit and branch lineage; preserve a route for historical replay.

A superseded implementation may be: marked inactive; wrapped by an adapter; placed
behind a compatibility interface; registered as experimental; isolated in a sandbox;
retained as a fallback; designated read-only; assigned to historical replay; or
converted into a benchmark opponent. It must not simply disappear.

---

## 3. One Source of Authority Does Not Mean One Source of Capability

Prevent multiple active authorities without destroying multiple implementations.
This distinction is mandatory.

**Authority.** There must be one authoritative answer for: what the Constitution
permits; which identity is acting; which legal principal is responsible; which
capability grant is valid; which policy version applies; whether an external action
may execute; whether an improvement may be promoted; which outcome becomes
institutional truth. These answers come from the canonical Kernel control plane.

**Capability.** There may be multiple implementations of: gates; ledgers; workflow
engines; strategy systems; memory systems; scoring systems; model routers; adapters;
business evaluators; experimentation engines. Do not destroy these alternatives.
Convert them into: implementations behind one interface; fallback engines;
experimental candidates; counterfactual twins; benchmark competitors; migration
sources; or specialized capability modules.

One authority. Many governed capabilities.

## 4. Use Build Your Own X as the Institutional Integration Library

Use each technology as an architectural pattern, not educational material.

### 4.1 Compiler Architecture

Build an Institutional Integration Compiler transforming repository artifacts into
machine-readable institutional objects: constitutional files into executable policy;
schemas into typed contracts; workflows into durable state machines; agent
descriptions into Agent Charters; business plans into Business Genomes; modules into
Capability Genomes; experiments into executable experiment plans; repository
manifests into Organ Manifests; approval policies into authority requirements; proof
artifacts into verifiable evidence references.

Compiler stages: DISCOVER → PARSE → CLASSIFY → NORMALIZE → TYPE-CHECK → RESOLVE
DEPENDENCIES → IDENTIFY AUTHORITY → GENERATE ADAPTER → STATICALLY VERIFY → REGISTER
→ SIMULATE → PROPOSE ACTIVATION.

The compiler must never silently invent missing authority, evidence, legal identity,
permissions, or dependencies. Missing information becomes an explicit unresolved
field.

### 4.2 Linker Architecture

Build an Institutional Linker connecting compatible capabilities from different
repositories (DALEOBANKS OpportunityPacket output → WealthMachine intake;
WealthMachine VentureAssessment → DALEOBANKS validation preparation; DALEOBANKS
external outcomes → Kernel causal memory; Kernel capability grants → organ-specific
adapters; Kernel evolution proposals → versioned configuration changes; WealthMachine
Venture Cells → Kernel authority and budget envelopes; DALEOBANKS audience
intelligence → WealthMachine opportunity discovery; WealthMachine validated offers →
DALEOBANKS distribution capabilities).

The Linker must resolve: contract version; identity; legal principal; permissions;
dependencies; data classification; authority ceiling; event inputs; event outputs;
error semantics; rollback; verification obligations; state ownership.

Do not directly couple modules where a typed institutional contract can connect them.

### 4.3 Package Manager Architecture

Build the Capability Genome Registry as an institutional package manager. Register
every useful capability found across all repositories, each with: capability
identifier; name; version; source repository; source branch; source commit;
implementation path; purpose; inputs; outputs; events consumed; events produced;
permissions; legal principal requirements; authority ceiling; data classes;
dependencies; optional dependencies; incompatible modules; health checks; tests;
adversarial tests; benchmark history; known incidents; performance distribution; cost
profile; attach procedure; detach procedure; migration procedure; rollback procedure;
recovery procedure; kill conditions; external evidence; maturity level; lifecycle
status.

Lifecycle statuses: DISCOVERED, SPECIFIED, WRAPPED, TESTED, SANDBOXED, SHADOW,
CANARY, ACTIVE, SPECIALIZED, FALLBACK, SUPERSEDED, HISTORICAL, QUARANTINED.

SUPERSEDED does not mean deleted. It means a stronger default exists.

### 4.4 Dynamic Linker and Plugin Architecture

Build a governed module loader capable of attaching and detaching capabilities
without redefining UNIIMENTE's identity. Every module declares: imports; exports;
required permissions; provided capabilities; required state; state namespace;
external targets; budget; time limit; consequence class; health signal; shutdown
behavior. Required operations: inspect, validate, install, attach, activate, pause,
shadow, compare, replace, rollback, detach, export-state, import-state, archive,
restore.

No module may: attach itself; activate itself; widen its own authority; alter its own
approval requirements; prevent detachment; hide its state; resist shutdown.

### 4.5 Version-Control Architecture

Treat every major institutional object as a versioned artifact (Constitution, policy,
authority matrix, Organ Charter, Capability Genome, Business Genome, Workflow,
Strategy Tree, Spider-Web Audit, Evolution Capsule, media canon, audience policy,
capital policy, validation protocol). Preserve ancestry, branch history, diffs,
signatures, reason for change, evidence supporting the change, rollback target.
Never overwrite the past. Create new versions.

### 4.6 Database Architecture

Build an Institutional State Fabric above mature databases: separate bounded data
stores; typed cross-repository events; shared identifiers; immutable provenance;
materialized institutional views; reconciliation workers. The repositories may retain
local state. The Kernel maintains the authoritative institutional relationship graph.

### 4.7 Event-Sourcing Architecture

Use a shared typed event spine to connect every organ. Every consequential
transition emits an event carrying: event ID; event type; timestamp; actor identity;
organ identity; legal principal; causal parent; correlation ID; contract version;
policy version; evidence references; sensitivity; integrity hash.

### 4.8 Distributed-Systems Architecture

Connect organs through durable patterns: transactional outbox; idempotent inbox;
signed messages; replay protection; causal ordering; retries; dead-letter handling;
compensation; reconciliation; circuit breakers; backpressure; degraded mode.

No message may become authority merely because it came from a trusted repository.
Every receiving organ revalidates: identity; contract; policy; evidence; authority;
freshness; target; budget.

### 4.9 Message Queue Architecture

Create an organ-neutral event transport interface with local and production
implementations (in-memory for unit tests; SQLite/file-backed for local durability;
PostgreSQL outbox/inbox for controlled deployments; optional mature broker adapter at
scale). Keep the institutional event contract independent of the broker.

### 4.10 Service Discovery and RPC

Build a Capability Discovery Service. Every organ publishes a signed manifest
listing: capabilities offered; contract versions; health; cost; latency; authority
requirements; evidence maturity; current availability. Discovery does not grant
access. Use typed service clients generated from contracts.

### 4.11 Operating-System Capability Security

Treat permissions as unforgeable narrow capabilities bound to Capability × Domain ×
Action × Resource × Target × Data Class × Consequence Class × Environment × Budget ×
Duration. A media-generation module does not inherit publishing authority. A
business-analysis module does not inherit spending authority. A memory module does
not inherit the ability to alter evidence. A swarm does not inherit the founder's
authority.

### 4.12 Containers, MicroVMs and WebAssembly

Containment by risk: hardened containers for trusted internal modules; stronger
isolation (microVMs) for untrusted tools and generated code; WebAssembly-style
component boundaries for portable narrow capabilities where justified. Competing
implementations must run without accessing secrets, altering policy, reaching
unrelated state, executing external actions, or consuming unrestricted resources.

### 4.13 Emulator and Digital-Twin Architecture

Every preserved legacy implementation becomes useful: emulators; shadow systems;
counterfactual twins; adversarial comparators; regression oracles; historical replay
targets. When two implementations disagree: preserve the disagreement; identify the
controlling assumption; construct the cheapest decisive test; compare external or
deterministic evidence; update routing weights; retain both when each dominates in a
different context.

### 4.14 Load Balancer and Cognitive Router

Build a Capability Router selecting among implementations by verified accuracy,
evidence maturity, latency, cost, privacy, domain fit, current health, failure
history, authority requirements, reversibility, environmental conditions. Routing
decisions are recorded and later compared with outcomes.

### 4.15 Search Engine and Knowledge Graph

Build one provenance-aware institutional knowledge graph connecting Repository →
Branch → Commit → File → Contract → Capability → Organ → Agent → Identity → Legal
Principal → Permission → Evidence → Claim → Contradiction → Prediction → Decision →
Action → Receipt → Outcome → Learning → Improvement → Business → Customer → Revenue
→ Capital Consequence.
