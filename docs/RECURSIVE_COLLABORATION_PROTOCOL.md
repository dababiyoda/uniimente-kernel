# Recursive Collaboration Protocol

This protocol turns collaboration, dissent, and founder-intent preservation into an auditable institutional process.

## 0. Founder-effect compilation gate

Before any material architectural interpretation of a founder statement, read `docs/FOUNDER_EFFECT_COMPILER.md` and `docs/intent/INTENT-0030-effect-not-metaphor.md`.

The governing rule is:

> **Preserve the effect. Do not literalize the metaphor.**

Biological, institutional, mythic, and science-fiction language is presumed to specify an intended capability/effect and provide mechanism-discovery inspiration unless Alfonso explicitly requires the implementation form itself.

Before implementation, record:

1. exact founder expression and lineage;
2. intended observable effect;
3. literal requirements;
4. metaphor/aspiration elements;
5. simplest conventional mechanism;
6. existing UNIIMENTE capabilities considered;
7. commodity/open-source/API/plugin/service/computer-use mechanisms considered;
8. transferable causal mechanisms extracted from the metaphor or source domain;
9. residual CapabilityDeficit;
10. falsification or verification condition for the underlying effect.

A design that cannot answer these questions is not ready for implementation.

Canonical morphogenesis means functional capability formation/reconfiguration in response to discrepancy. MICA/CDPE, cells, tissues, local-rule systems, decentralized topology, and OMNIMORPH organization hypotheses are optional mechanism candidates, not mandatory definitions of morphogenesis.

## 1. Required review roles

Every material architectural change must receive explicit analysis from five roles. One person may perform multiple roles, but each perspective must be recorded separately.

1. **Builder** - strongest implementation case, including effect fidelity and simplest viable mechanism.
2. **Adversary** - strongest failure, abuse, drift, literalization, and counterexample case.
3. **Operator** - deployment, maintenance, observability, recovery, resourcefulness, vendor/tool choice, and cost.
4. **Beneficiary Representative** - participant welfare, accessibility, dignity, consent, privacy, and externalities.
5. **Constitutional Reviewer** - authority, evidence, legality, reversibility, shutdown integrity, and protection against self-authorizing capability growth.

Disagreement is preserved. Consensus is not manufactured.

## 2. Mandatory alternatives

Every proposal must compare at least:

- proposed design;
- simplest viable design;
- strongest competing design;
- do-nothing / preserve-current-state option;
- staged or reversible experiment.

When a CapabilityDeficit or metaphor-derived requirement is involved, alternatives must also include real-world acquisition routes where applicable:

- existing registered capability;
- composition/reconfiguration of existing capabilities;
- mature commodity infrastructure;
- open-source project or library;
- API, plugin, connector, model, or service;
- authorized computer-use workaround;
- small generated adapter/utility;
- external/internal coding agent;
- temporary specialist organization;
- genuinely new architecture.

The proposal must explain why it skipped any materially simpler route.

Each alternative records benefits, liabilities, evidence, dependencies, migration cost, rollback path, and kill criteria.

## 3. Two upward passes

A proposal cannot be marked ready until it completes exactly two strengthening passes.

### Pass 1 - structural inversion

For every advantage:

- identify how it can become a moat, default pathway, interoperability advantage, proof advantage, cost advantage, or participant-welfare flywheel;
- identify the condition under which the advantage reverses into a liability.

For every disadvantage:

- remove it;
- bound it;
- make it observable;
- make it reversible;
- or convert it into a useful constraint, test, modular boundary, market signal, or governance advantage.

Pass 1 must explicitly ask whether the architecture exists only because a metaphor was taken literally. If the same target effect can be achieved more simply using existing technology, the burden of proof is on the more elaborate design.

### Pass 2 - adversarial compounding

Re-attack the strengthened design as though Pass 1 were already deployed.

- Find new concentration, complexity, incentive, authority, security, maintenance, adoption, evidence, tool-proliferation, vendor-dependence, and literalization risks.
- Strengthen the design again.
- A Pass-1 downside may not disappear from the record. It must be resolved, accepted with a named owner and threshold, or converted into a kill condition.
- Attack the claimed **underlying effect** separately from the implementation's internal success metrics.

## 4. Merge proof

A material change is mergeable only when the record contains:

- founder-intent references;
- target effect and metaphor/literal split when relevant;
- system boundary affected;
- existing mechanisms searched;
- residual CapabilityDeficit;
- all alternatives;
- five-role debate;
- Pass 1 and Pass 2 maps;
- explicit unresolved dissent;
- evidence and counterevidence;
- tests and verifier strength;
- falsification condition for the claimed effect;
- migration and rollback plan;
- operational owner;
- kill criteria;
- decision: `retain`, `regress`, `kill`, `defer`, or `experiment`.

No document, model output, majority vote, reputation score, or reviewer enthusiasm authorizes production effects. The Consequence Gate and human constitutional authority remain final.

A generated or acquired capability is not authorized merely because it passes tests. Building != installation != activation != consequence authority.

## 5. Collaboration norms

- Critique claims and mechanisms, not people.
- Steelman before rejecting.
- Preserve contributor lineage and rejected branches.
- Prefer narrow contracts over duplicated implementations.
- Prefer reversible experiments over argument when the decisive uncertainty is testable.
- Prefer existing mature mechanisms over new frameworks when they achieve the same effect.
- Treat open-source repositories and external tools as mechanism/capability sources, not cloning mandates.
- Preserve the founder's high-level aspiration even when current technology cannot yet fully realize it.
- Escalate irreducible value conflicts to the founder.
- Record negative and zero results.
- Never hide scope, assumptions, unresolved risk, contradictory evidence, or unsupported capability claims.
- Optimize for shared capability and market health, not collaborator dependence.

## 6. Recursive application

This protocol applies to itself. At each major release, audit whether it improves decision quality, contributor comprehension, cycle time, defect escape rate, duplicated work, founder-intent fidelity, effect fidelity, and avoidance of unnecessary architecture. Retain, revise, or regress it based on measured outcomes.
