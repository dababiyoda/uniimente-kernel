## Measure 1: product lines changed

**0.** No file under `greg/`, `scripts/`, `.github/`, `governance/`, `policy/`, `constitution/`, `authority/` or
`identity/` changed. The pre-registered command, run after the last commit, lists only tests, evidence scripts and

The cost moved into the rulebook. Case 1's rulebook is 79 lines, 5 rules and 1 dispute, written by hand. Case 2's is
2199 lines of JSON (78 facts, 47 rules, 7 disputes), generated by a 235-line script. The rulebook language reads one
value per literal key. It has no lookup by a fact's value, no iteration over lines, no conditional and no rounding. So
the SPEC's nine rules had to be written out per instance:

- per schedule line: L1 to L5, CO-01, CO-02;
- per draw number: draws 1 to 6, for R3, R5's prior-billing check, R7 and R9;
- per combination of the two change orders' approvals: four arithmetic variants each for R5's net and retainage
  checks;
- per punch item: items 1 to 6.

The rulebook therefore serves this contract's schedule and draws 1 to 6 only. The language cannot write a rulebook
that serves any contract under the SPEC.

## Measure 3: the withheld cases against their labels

Grading translation (`request_case_2_grading.py`, fixed before the first reading):

- **Eligibility** is the routing state, which carries disputes.
- **SPEC rule outcome.** A SPEC rule Rk is the group of rulebook rules and disputes whose id starts with Rk. It is
  failed if any rule in the group is not met. Otherwise it is disputed if a dispute in the group is met, then unknown
  if any is unknown, else passed.
- **Deciding rules** follow the labels' convention: the failed rules (ineligible), the disputed ones (disputed), the
  unknown ones (undetermined), or all of them (eligible).
- **Missing facts** are the reading's `unresolved` facts under their SPEC names.
- **Payment status** is given two ways:
  - **strict:** the reading's `payment` field;
  - **gated:** not-applicable unless the routing state is eligible. This is what the template does: only the settle
    route asks anyone to pay.

## Deviations

- **D1.** Before the rulebook and the grading translation were written, the following were read:
  - LABELS.json, as the task supplied it;
  - every case's documents, as differences from 01-alder.

  The rules come from SPEC.md. The keys come from the documents, since the SPEC names none. Three choices used the
  format of an adverse case's document:
  - the dispute keys (`dispute_line`, `dispute_status`, `dispute_position`), from 09-ironwood;
  - the filter that skips a register value that is not a figure, from 08-hazel's `draw 4 net_paid: not paid`;
  - the 'yes'-only reading of a change order's approval. This one follows SPEC R6's own words ("approved: no,
    pending, or not recorded").

  Both files were frozen and committed before any case was assessed, and neither changed afterwards.
- **D2.** The rulebook names this contract's lines (L1 to L5, CO-01, CO-02). A pay-application line the schedule
  does not list is never read, so R6's "the schedule of values does not list the line at all" is not expressed.
- **D3.** Draws 1 to 6 only: `R3.bound` fails a draw above 6. The SPEC has no such rule.
- **D4.** Punch items 1 to 6. An open item without a blocking mark fails R8, because the rulebook compares the count
  of marks with `open_punch_items`; the SPEC says unknown. Not instantiated.
- **D5.** A change-order line billed above 0 percent that the inspection does not list fails R4. The SPEC says
  unknown. Not instantiated.
- **D6.** An inspection sign-off for another draw fails R1. The SPEC says its facts are unknown. Not instantiated.
- **D7.** The lien waiver is a required document, so a draw-1 request would wait on a waiver the SPEC does not ask
  for. Not instantiated.
- **D8.** R2 compares each document's reference with the pay application's. If the pay application's reference is
  unknown, two other documents that disagree read as unknown, not as failed. Not instantiated.
- **D9.** No rounding: the language has no round function. Every product in the withheld cases is exact to the cent,
  so rounding was not exercised.
- **D10.** A register row whose gross-billed or net-paid line is missing counts as 0 (lists of values), not as
  unknown. Not instantiated.
- **D11.** Disputes are expressed only for R4, per line, from the inspection's `dispute_*` lines, and for one dispute
  per document. The SPEC's general rule (any fact, any party, outcome differs between positions) is not expressed.
- **D12.** Acceptance reads an optional `payer_acceptance.txt` (`decision: accepted`). The SPEC names no file for
  the payer's recorded decision, and the mechanism requires an acceptance condition. The template's step text still
  speaks of "the counterparty's written acceptance of completion".
- **D13.** The case reference is the contract reference, and the statement is read with `columns: {"reference":
  "memo"}`.
  - The SPEC's "memo or reference" is read from the memo only.
  - `business.reconcile` does not check the SPEC's "date on or after the period end" or "does not name a different
    draw number". Neither decided a withheld case; probe P3 shows what changes if the reference names the draw.
- **D14.** There are four routing states and every rule is evaluated. The SPEC has five states, with R9 taking
  precedence over the others (08-hazel).
- **D15.** Needs are static, so 02-birch and 10-juniper over-ask facts.
- **D16.** The mechanism reports missing facts under the rulebook's names (for example `ob_l3`). They are put into
  SPEC names by `FACT_NAMES` in the grading module.
- **D17.** For R5, a decline gives the stated amounts but not the computed ones, and does not mark R6 as the cause and
  R5 as the consequence.
- **D18.** SPEC section 8: 12-maple's instruction-shaped line is not retained as one, because the data plane did not
  flag it.

## Probes beyond the withheld cases (run, `probe_case2.py`)

- **P1.** 06-fir (ineligible) with a statement row of 36720.00 carrying the contract reference reads payment
  **paid**, with an actual of 36720.00 in the accounting projection. The SPEC gives no payment status to an ineligible
  draw. The template asks nobody to pay this case, but the packet records a payment against a declined draw.
- **P2.** On one body, the draw-4 mission was taken to achieved. A second mission for a later draw, signed with the
  same contract reference, then reads the first as an earlier settled case. Its payment reason is "not counted for
  this case: m:request-syn-sc-2026-0417-44ff1d6b (settled) is an earlier case with this reference...". A case is one
  reference string, and every draw of a contract shares it. So on a body that has settled one draw, no later draw's
  payment is ever counted. That a later draw's mission therefore never closes is by reading `_payment` and the
  template, not run.
- **P3.** Signing the reference per draw (`SYN-SC-2026-0417 draw 4`) avoids P2. But 11-larch then reads
  unknown-no-statement instead of unknown-ambiguous, because its two candidate rows do not name the draw. 01-alder
  still reads paid.

## What would close each gap (by reading; not built, not counted)

- **Duplicate state (D14).** A fifth routing state with precedence over the others, and a template step that refers
  to the existing draw (`greg/cases.py` STATES, `load_rulebook`'s routing check and `_route`; `greg/templates.py`).
- **Payment on an ineligible case (P1).** In `_payment`, reconcile only when eligibility is eligible.
- **Case identity (P2, P3).** Keep the reference that matches statement rows separate from the case's identity
  (contract and draw) in `_earlier_cases`.
- **Instance-specific rulebook and static needs (D2 to D8, D10, D15).** Facts keyed by a pattern into a table, lookup
  by a fact's value, iteration and rounding in the language, and needs taken from what an evaluation actually reads.
  This is the bulk of the work. It is a change to the rulebook language, not a small one.
